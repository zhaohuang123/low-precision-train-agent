# `code-change` 深化材料：定位路线 / 「表达不了」清单 / patch 纪律

> 本文件是 `skills/code-change/SKILL.md` 的**渐进披露层**：正文只留入口一句话，长内容在这里。
> 纪律：具体框架路径／模型名／阈值**不在本文件** —— 框架检出由 `config/tasks/<任务名>.yaml` 的 `train.framework_repo`
> 给出，框架能力证据由 `knowledge/frameworks/*.md` 带 `file:line` 给出。

## 1. 定位路线（先定位，再改；顺序不许颠倒）

1. **确认哪棵树在生效**：改源码树还是改 site-packages，结论会随装机状态变，**别背结论**：
   ```bash
   python3 -c "import <框架包>; print(<框架包>.__file__)"
   ```
   出现「文件改了、守卫测试绿了、训练行为没变」这种最费时间的循环，根因通常在这里。
2. **找注册表/choices**：框架用一张注册表决定「哪个方案名 → 哪份实现」。**没注册的改动等于没改**；
   传进去的方案名不在 choices 里 ⇒ 被忽略或直接报错。
3. **grep 机制名**（先确认位置再编辑）：机制名从 `design.md` 的受控块里取（轴名／取值），不要凭记忆。
4. **找守卫测试**：改完先跑它，再谈冒烟；测试文件名以现场 `ls` 为准。
5. **判 patch 目标会不会命中**（最危险的一条）：读「决定 patch 哪个模块」的那段逻辑，对着**实际模型模块名**核对。
   命中不上 ⇒ **一点量化都没做**，而日志仍然写着方案名 —— 这是本 skill 存在的理由。

**判据**：**读到 `file:line` 才算核过**；只说「框架应该支持」不算（同一条纪律：证据要能指到 `file:line`）。

## 2. 「表达不了」的清单（缺哪一类要指名）

| 缺失类别 | 表现 | 典型后果 |
|---|---|---|
| 参数缺失 | `--<方案名>` / 开关在当前 choices 里不存在 | 传进去被忽略或报错 |
| 内核缺失 | 没有对应的 fake-quant 内核（旋转/随机舍入/块大小/缩放策略） | 只能自己写内核，通常超本轮预算 |
| 层选择缺失 | 没有层过滤/回退分支 | 做不了「只压某类层」或「回退某几层」 |
| **patch 目标对不上** | 决定 patch 哪段模块的逻辑与实际模块名不一致 | **最危险**：量化根本没做，日志却写着方案名 |

**融合结构是「表达不了」的常见来源**：训练侧把两个投影融合进**一个**线性层（典型一例：
gate 与 up 投影融合成一个矩阵）⇒ 其中一个**无法单独按名豁免**。出路只有两条：
① 给 patch 把这个分支拆出来；② 整层不豁免（该变量走原生取值）。**不许**用注释开关假装豁免了。

## 3. patch 三栏 ＋ 挂/还原纪律

每份 patch **必须带三栏**：**改了哪个文件 / 为什么 / 怎么验证**。

```bash
# ① 按需切干净工作树：起点 = 本轮钉点（config/tasks/<任务名>.yaml 的 train.framework_head）
FR=<框架检出>; WT=<工作树>; P=<轮次>/patches; Q=0001-<简述>.patch
git -C "$FR" worktree add "$WT" <framework_head>
git -C "$WT" apply --check "$P/$Q" && git -C "$WT" apply "$P/$Q"
# ② 跑实验
# ③ 跑完（正式步骤）：还原 + 机械校验；前后 rev-parse HEAD 与 status --porcelain 的 diff 任一有差异 ⇒ 本轮失败
git -C "$WT" apply -R "$P/$Q"
```

两条铁律：**框架检出本身永不提交改动**（`git status --porcelain` 必须为空）；**改动用 patch 挂进去、跑完即还原**。
挂载统一 `git apply`（**不用软链** —— 软链在「还原」上会留下悬挂链接）。落点：单轮改动 `<轮次>/patches/`；
只有**跨多轮复用、已证明稳定**的才进 `knowledge/frameworks/patches/`。

## 4. 静默降级反模式（一律 `CODE_FAILED`，不是"想办法绕过"）

1. **训练侧全量化、评测侧部分回退**（或反之）⇒ 两者不是同一个东西，聚合差不能归因给方案。
2. `except: pass` 吞掉不支持的分支。
3. 把方案名照抄进日志，实际走默认路径。
4. 填假参数／注释开关／改配方，让它「看起来跑通」。

**判据**：`CODE_FAILED` 必须指名「哪个文件／哪个内核／哪个 choices 不支持」＋「缺的是哪一类能力（上表四类）」
＋ 替代路径或明确写「不做的理由」。

## 5. 机制生效验证命令的最低要求

- 至少**一条可复现命令**给出「生效」的直接证据（探针计数、命中行、sha 比对…），而不是「文件被改了」。
- 先问「**这段代码在什么条件下才执行**」，再把验证放到那个条件下；条件跑不了（例如需要真卡）就**明写「该分支未被覆盖」**，
  别让一条恒绿的断言冒充覆盖。
- 训练侧与评测侧做**逐项对齐表**（方案名／量化范围／格式与块大小／旋转与舍入／ckpt 是否已折叠旋转），
  由 tester 在冒烟阶段**复跑**（「机制真装上没」的验证证据归 developer 给、tester 复跑）。
