## 1. 退出码归类（先归类，再解释）

| 码 | 含义 | 归类依据 |
|---|---|---|
| `0` | 成功 | 退出码 ＋ 末行产物路径 |
| `1` | 未分类的运行期失败 | 段内命令失败且未归类；日志里第一条 traceback |
| `2` | 约定/契约/门不过 | 配置校验、门、根解析、目标已被改过；**不是运行期偶发** |
| `5` | 训练侧无效：发散/NaN，**以及墙钟超时**（都由任务配置的阈值触发、都杀整个进程组；**平台早停 `converged` 不在此列，它归 `0`**） | 触发的是任务配置 `stop_conditions.loss.*`／`quant_error_max`／`wall_clock_hours` （**不在判据里**，0.18.18 起） |
| `6` | 评测侧无效（口径不全、驱动异常、结果不可比） | 评测口径对账失败／驱动自证缺失 |

**判据**：写出归类与**依据行**（`file:line` 或日志行）；**不许把 5/6 含糊成 1**（一个是「有归类的无效」，一个是「还没归类」）。

> **旧工程 → 本工程的变更（P4 已定，不再悬置）**：旧三段脚本把 `5` 记作**在线早停触发**、把 `6` 记作
> **墙钟上限超时**；本工程把码按「**哪一段无效**」切 —— `5`＝训练侧无效（发散/NaN **＋ 墙钟超时**；平台早停 0.18.26 起归 `0`）、
> `6`＝评测侧无效（旧表**没有**这一码，口径不全只能含糊成 `1`）。完整对照表与理由在 `runtime/README.md` §2.1。

## 2. 早停/观察两道：本工程只有一个 `loss.min_points`

本工程判据字段是 `stop_conditions.loss.{jump_factor, rel_to_best, min_points}`（＋ `wall_clock_hours`）。
分两道看：

| 道 | 看什么 | 触发后 |
|---|---|---|
| **在线早停 · `invalid`** | 只看**已经发生**的步（`jump_factor` 比相邻步、`rel_to_best` 比末步/最好步），命中即**杀整个进程组** | 跳过转换与评测，报 `EXPERIMENT_INVALID` |
| **在线早停 · `converged`** | 同一套阈值，命中「走平」（平台） | **不跳过**：退出 `0`，转换/评测照常；报告写明「停在第 N 步」 |
| **离线轨迹** | 整条轨迹（点数 ≥ `min_points` 才下结论），进程结束后观察形状 | 本轮不产生精度结论 |

**为什么必须一起看**：本工程记录过真实形态 —— 相邻两步 loss 从 `2.02` 涨到 `18.4`（`9.09` 倍），
**两个值都是有限值**，只查 NaN/Inf 完全没触发，于是白跑了一次完整训练。
**判据**：早停命中时记三项齐全 —— **哪个阈值、第几步、什么数值**（例如「第 2 步相邻跳变比 `9.09`」）。

## 3. 轨迹判读实例（形状，不是单点）

| 形状 | 现象 | 结论方向 |
|---|---|---|
| 单调下降后平台 | 末段几乎不动 | 正常收敛；是否达标看评测 |
| 平台后突降 | 中段有台阶 | 可能是调度/数据序；要么复验要么归因 |
| **有限值但已发散** | 相邻步大幅上升（如 `2.02 → 18.4`） | **训练侧无效**（`5`）⇒ `EXPERIMENT_INVALID` |
| 抖动无趋势 | 上下无明显方向 | 点数不足或本预算下不可分辨 ⇒ **不下结论**（写 `null` ＋ 理由） |

**判据**：点数与形状都写出来；点数 ` < loss.min_points` ⇒ 不下结论；点数不足时**不许**用「趋势向好」补话。

## 4. 日志解析：不要自己重写 loss 正则

loss 行的**唯一解析器**是 `runtime/metrics.py`（loss 轨迹正则全工程唯一一份，别自己重写）。
两条实测约束：

- 日志里的 loss 是**科学计数法**（形如 `lm loss: 9.896337E-01`）⇒ 自写正则漏掉指数会把 `9.896337E-01`
  读成 `9.896337`，**凭空造出一个约 9.9 的"发散"**。
- `rel_to_best` 一类量的分母口径（「运行中的最小值」而不是「全程最小值」）由抽取器定义；
  自己重算会得到另一个数。

**判据**：观察用的数字一律来自 `metrics.json` 或抽取器；**不许自己写解析器**再拿它的输出当证据。

## 5. 残留进程与框架还原：跑完的两个机械检查

1. **进程组**：早停/超时都必须杀**整个进程组**（不是只杀父进程）。检查残留：
   ```bash
   pgrep -af '<训练入口或 executor 的进程名>'      # 期望：无输出
   ps -eo pid,pgid,etime,cmd | grep -F '<进程名>' # 有则确认 pgid 与残留
   ```
   残留会占住卡，让下一轮莫名 OOM。
2. **框架还原校验**：`<轮次>/patches/framework_{head,status}.{before,after}` 四份快照的 diff **必须为空**
   （`runtime/framework_patch.sh verify`）。有差异 ⇒ **本轮失败**（结果与上一轮互相污染）。

**判据**：两类检查的**实际输出**落进 `<轮次>/evidence/`，不是只在终端里看一眼。
